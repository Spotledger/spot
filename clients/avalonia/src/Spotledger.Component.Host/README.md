# Spotledger.Component.Host

The desktop half of the tier B component story (WP-UI-14.T2): it reads a signed package, verifies
it with the same Ed25519 scheme app bundles use, loads accepted assemblies into a collectible
`AssemblyLoadContext`, and drives install, upgrade, uninstall, failure isolation and view binding.

A component is **reviewed and signed** code. The load context gives it a lifetime and a dependency
space; it is **not a sandbox**, and nothing here claims otherwise.

## 1. Package layout

```
acme.rating-1.0.0/
  component.json                     the manifest (signed)
  component.sig                      standard base64 of the 64 signature bytes
  assemblies/Acme.RatingComponent.dll
  assets/acme-rating.json            optional
```

`component.json` is a closed JSON object — an unknown member is refused, so a typo cannot silently
drop a rule:

| Member | Type | Meaning |
| --- | --- | --- |
| `component_id` | string | The dotted lowercase id, e.g. `acme.rating`. |
| `component_version` | string | The component's own SemVer, e.g. `1.0.0`. |
| `display_name` | string | 1–64 characters, shown in a picker. |
| `publisher_id` | string | The publisher the certificate must name. |
| `contract_range` | object | `{ "minimum": "1.0", "maximum_exclusive": "2.0" }`: exactly one major. |
| `entry_assembly` | string | The package-relative path of the assembly that exposes the descriptor. |
| `assemblies` | array | `{ "path": …, "sha256": … }` for every assembly. |
| `assets` | array | `{ "path": …, "sha256": … }` for every asset; may be empty. |
| `key_id` | string | 32 lower-case hex characters: the id of the signing key. |
| `signed_at` | integer | UTC seconds; the publisher's signing time. |

Paths are relative, use `/`, have no `.`/`..` segment, no drive and no backslash; the reader refuses
anything else before it opens a file. `sha256` is the lower-case hex SHA-256 of the file's bytes: a
package whose bytes changed after signing is refused before any assembly is read.

## 2. Canonical bytes and the signature

The signed bytes are **domain bytes followed by canonical JSON**, exactly as
`crates/framework/spot-bundle-signing/src/canonical.rs` writes them:

* one JSON object whose keys are sorted (ordinal), with no whitespace;
* integers only — no number form holds a fraction, so money and quantities cannot be signed by
  accident;
* strings escaped as serde_json escapes them: `\"`, `\\`, `\b`, `\f`, `\n`, `\r`, `\t`, every other
  code point below `U+0020` as `\u00xx` (lower-case hex), everything else as raw UTF-8;
* base64 is the standard alphabet with padding.

Domains:

| Domain | Bytes |
| --- | --- |
| Component manifest | `SPOT-COMPONENT-MANIFEST-V1\n` |
| Publisher certificate | `SPOT-PUBLISHER-CERT-V1\n` |
| Revocation list | `SPOT-REVOCATION-LIST-V1\n` |

The manifest's canonical object has exactly the members of the table above, with
`contract_range` as `{ "maximum_exclusive", "minimum" }` and each file as `{ "path", "sha256" }`,
file lists sorted by path. The signature file carries the detached Ed25519 signature over
`SPOT-COMPONENT-MANIFEST-V1\n || canonical(manifest)`; nothing else is signed, and the file on disk
is not: whitespace and key order in `component.json` do not matter.

`key_id` is the first 16 bytes of the SHA-256 of the 32-byte Ed25519 public key, lower-case hex (32
characters) — the same derivation `spot-bundle-signing` and `spot-signed-command` use. Public keys are
32 bytes, signatures 64.

The test vectors in `clients/avalonia/tests/Spotledger.Component.Host.Tests/Vectors/component-signing-vectors.json`
are generated by a program that links the real `spot-bundle-signing` crate: canonical bytes, key ids,
a publisher certificate, a revocation list and four manifests (plain, awkward strings, compromised
signer, wrong key). The C# host and the Python shell tool are both tested against those bytes.

## 3. Trust, rotation and revocation

`ComponentTrustStore` is filled from the store registry: store roots, the publisher certificates they
issued, and the current signed revocation list. It holds public keys and signatures only.

* A certificate is accepted when a trusted root's window covers `now` and the root's signature over
  the certificate body verifies.
* **Rotation** is a second certificate for the same publisher with a new key and its own window. A
  package is checked against the certificate its key names at `now`; a package signed with the new
  key verifies as soon as the store ships the new certificate. `signed_at` is written by the
  publisher, so no decision rests on it; where it is shown it is labelled "claimed by the publisher".
* The **revocation list** is the bundle-signing mechanism unchanged: signed by a store root, its
  `generation` must be strictly higher than the held one: a lower list is `component.revocation.stale`
  and an equal one (even validly signed, with other contents) is `component.revocation.generation_not_newer`.
  A listed key or publisher refuses everything it signed or published, whatever date a package claims;
  `effective_from` stays in the wire format and is shown to an admin but decides nothing, and
  `compromised` only picks the code. Package digests can be revoked too (the SHA-256 of the signed
  manifest bytes). Accepting a list re-checks everything installed (`RecheckInstalled`): a revoked
  component is disabled (no new instance, instances disposed, context unloaded; if it cannot be
  unloaded the host sets `RestartRequired` and keeps refusing), reported as a `RevocationOutcome`, and
  remembered in the install state so a restart does not re-enable it. This stops further use; code
  that already ran in this process had its full authority.
* **A revocation that cannot be saved is reported.** `RecheckInstalled` writes the disabled set to the
  install state. If the store cannot be read or written (it fails or throws), the outcome carries
  a `PersistenceFailure` with the stable code `component.revocation.not_persisted`, the host logs the
  refusal, sets `RestartRequired`, and `Install` and `Upgrade` refuse every package with that code
  until `RetryPersistRevocations()` has saved the disabled set. The message never carries the
  store's own error text, so a path in an exception does not reach the UI.
* **Install memory.** The host persists per component id the highest version installed and the
  highest revocation generation installed under (`IComponentStateStore`). An older version is
  `component.version.downgrade_refused` unless the caller passes `InstallOptions(AllowDowngrade: true,
  Actor: ...)`, which is written to the install log; revoking the newer version is the normal way back.

**No wall clock.** `now` is an argument to every check; nothing in this package reads
`DateTime.UtcNow`, `DateTimeOffset.Now`, `Stopwatch` (other than the injected `StopwatchClock` the
shell passes) or `Environment.TickCount`.

## 4. Verification order

`ComponentVerifier.Verify` runs these checks in this order and reports the first failure with its own
stable code:

1. the signing key is one a trusted publisher certificate names — `component.signature.unknown_key`;
2. that certificate names the manifest's publisher — `component.publisher.mismatch`;
3. the certificate's window covers `now` — `component.certificate.not_yet_valid` /
   `component.certificate.expired`;
4. the publisher, the key and the package digest are not revoked —
   `component.publisher.revoked`, `component.key.revoked`, `component.key.compromised`,
   `component.package.revoked`;
5. the Ed25519 signature verifies — `component.signature.invalid`;
6. the contract range contains this host's contract version — `component.contract.too_new` /
   `component.contract.unsupported`.

A refusal names a package file by its zero-based index and a sanitised relative path
(`ComponentRefusalText.FileRef`: printable ASCII only, anything else replaced with `?`, cut at 120
characters) and never the package directory, because it is shown and logged before the signature has
been checked and the names come from the package.

Reading the package (`ComponentPackage.Read`) has already refused a missing manifest, a missing or
malformed signature, a missing, unreadable, truncated or oversized file, too many files, two
assemblies with one simple name, an unsafe path, any symbolic link or reparse point inside the
package (`component.package.symlink_refused`) and any hash that does not match (the message names the
file and prints no hash), each with its own code and never an exception. Every refusal is logged
through `IComponentHostLog`. The link check and the read are two steps: a writer who can change the
package directory while it is read can still race them, so the directory should be writable only by
the installer.

## 5. Loading

Only after verification does `ComponentLoader` create a `ComponentLoadContext`. Two rules decide what
a package may resolve:

* the assemblies it ships (its own bytes);
* the assemblies the host shares — the contract, `Spotledger.Component.Contract`;
* the platform: the BCL and Avalonia, which the process already runs, from the default context.

Every other `Spotledger.*` assembly is the application's private code; a reference to one is refused
with `component.dependency.host_private`, naming the assembly, **before** the context exists (the
reference table is read from metadata, never executed). The context records any late attempt in
`RefusedAssemblies` as a second line of defence.

The entry point is a public static member of type `ComponentDescriptor` in the entry assembly:
`Instance` first (the T1 sample's name), then `Descriptor`. Its id, version, publisher and contract
range must equal the manifest's (`component.entry.descriptor_mismatch`), its own `Validate()` must
pass, and the contract registry's compatibility rules must accept its range. The descriptor is then
registered in the host's `ComponentCatalogue`.

Each file is read once into memory, its SHA-256 is checked on those bytes, and the assembly is
loaded from the same bytes (`AssemblyLoadContext.LoadFromStream`); the file on disk is never read
again, so a writer who swaps it after the check changes nothing the host loads. No file of
a package needs to be on disk after the read.

The context is collectible. Uninstall disposes every instance (which unsubscribes the host's
callbacks), removes the catalogue entry and calls `Unload()`; `UninstallAndTrack` returns a weak
reference to the context, and `tests/probes/UnloadProbe` proves in a process of its own that the
context is collected.

Two things matter for that to be true, and both were found by the test rather than by reading:

* a context **must not hold its own assemblies in a field**. `LoadPackageAssembly` therefore looks a
  loaded assembly up in `AssemblyLoadContext.Assemblies` instead of caching it; a context that caches
  one is never collected, so `Unload()` would leave the package's code in the process for good.
* the proof needs a separate process. The xUnit v3 runner keeps the assemblies a test loads, so a
  context that a test unloads is never collected inside the test host. `UnloadProbe` does the same
  install, uninstall and weak-reference check in a plain process and exits non-zero when the context
  outlives the uninstall.

### Limits of unloading and revocation

* **Components are not sandboxed** (a recorded security finding: accepted risk until isolation exists). A component runs
  in this process with this process's privileges.
* **A revoked, loaded component keeps running until the process exits.** `Disable` stops new
  instances, disposes the live ones and unloads the context, but a thread, timer or native handle a
  component started is not stopped by that. The unload probe (`tests/probes/UnloadProbe`) proves
  that the load context is **collectible**; it does not prove that a component's threads stopped.
* **A revocation of a component that has run therefore sets `RestartRequired`** (also when the
  context could not be unloaded or the revocation could not be saved), and raises
  `ComponentInstallationService.RestartRequested` with the stable code `component.restart.required`.
  The shell must listen to that event (or read `RestartRequired`) and tell the user to restart the
  application; the host itself shows nothing. A component that was installed but never created an
  instance has not run component code, so revoking it does not ask for a restart.

## 6. Lifecycle, failures and the guard

* `ComponentInstallationService.Install` = read, verify, load, register.
* `Upgrade` verifies and loads the new package first and only then tears the installed version down,
  so a bad upgrade leaves the working version running.
* `Uninstall` disposes instances, clears registrations, unloads the context.
* `ComponentSlot` catches a component that throws in its constructor or in an update and shows a
  placeholder control plus a `ComponentSlotError`; the form keeps working.
* `ComponentResourceGuard` measures a constructor or an update against an injected deadline with an
  injected `IMonotonicClock`. A constructor overrun is refused (and the instance discarded); an
  update overrun is logged, because a synchronous managed call cannot be aborted. **This is a
  diagnostic guard, not a sandbox:** a hanging component still hangs its thread.

## 7. View binding (and the gap it papers over)

A view may name a component with `{"component_id": "acme.rating", "props": {"max": 5}}`
(`ComponentReference`). The resolver checks the field type and validates the props against the
component's own props schema before an instance exists; with no reference it picks the installed
component that renders the field's type, by id.

`contracts/ui-ext` is tier A only ("Tier B … is WP-UI-14") and `spot-views`' `ViewDef` has no
component field, so there is no agreed place to put that reference yet. `ComponentReference` is the
smallest honest seam: a string a view definition can carry, parsed and validated here, with no
contract change. It is listed as an open question in the task's PR. Note the consequence of the
smallest seam being the only one: a component chosen with no reference gets no props, so a component
whose schema requires one is refused at that point rather than created with unvalidated props.

## 8. The browser shell's component set

A browser shell cannot load packages at run time: the tenant's set is chosen at build time, verified
and statically included. `tools/component-shell/build-shell.py` does that step and writes
`component-set-<hash>.json`, a manifest whose file name is the first 16 hex characters of the SHA-256
of its own bytes. `ComponentSetManifest` reads it (a closed document, entries sorted by id),
`ComponentSetManifestReader` refuses a file whose bytes do not hash to its name, and
`ComponentSetManifest.Compare` answers whether what the host installed is what the build listed — a
listed component that is missing, an installed component the build did not list, and a version or
signed-manifest digest that moved, each with its own code.
